tqdm 压缩实验对比

三次实验都把 tqdm 压到原来的 53%–59%，都没达到 50% 的体积目标。fact-rules 是唯一既通过验收、又让 25 个叶子都有有效测试的一次，但体积最大。graph-contract 体积最小，却丢了 3 个模块路径。field-fixes 的检查全部通过，但 monitor 叶子没有有效测试，所以按有缺口交付，耗时和花费也最高。

运行中记录的问题

graph-contract

  1. plan 拒绝了一条手写的 interface 句子，改写后通过。
  2. 启动前的预检 scope-baseline 被拒，属于文档写明的行为。
  3. 第 2 次保存因作者写了验证方的文件被拒，作业自行修复。
  4. 第 5 次保存因同样原因被拒，作业自行修复。

field-fixes

  1. 预检 scope-baseline 被拒，同左。
  2. 控制器第 7 轮的指令超过 4,000 字符，整轮作废，作业退回默认修复步骤。
  3. 第 7 次保存因重合度被拒，一次重写后放行。
  4. monitor 叶子的测试提案被评审否决后没有再设计，作业按有缺口交付。

fact-rules

  1. 预检 scope-baseline 被拒，同左。
  2. run-progress --metrics 传内联 JSON 被拒，是操作输入问题，只影响进度页。
  3. 第 4 次保存因重合度被拒，作业自行修复。
  4. 第 7 次保存因重合度被拒，作业自行修复。

三次运行都没有改 nanolize 的代码，也没有关闭检查或放宽验收标准。
